01

목적과 설계 목표

이 서브시스템은 "우리 마케팅 RAG 에이전트가 같은 문제를 예전보다 더 잘 풀게 됐는지"를 신뢰할 수 있게 측정한다. 핵심 난제는 단 하나다 — 채점을 또 다른 LLM에게 맡기면, 그 LLM이 학생을 돕거나(정보 누출) 채점 기준을 몰래 바꿔(점수 조작) 시험 전체가 무의미해진다는 것.

설계 전체가 그 오염 경로를 구조적으로 차단하는 데 맞춰져 있다. Judge는 에이전트가 쓰는 LLM_MODEL·tool·prompt·retrieval route와 독립된 evaluation adapter이며, 아래 네 원칙이 모든 결정을 지배한다.

Principle 01

채점관은 에이전트가 아니다

Judge 설정은 에이전트 모델 설정에서 절대 상속되지 않는다(config.py). 모델은 gemini-3.7-flash로 고정, tool 없이 구조화 출력만 반환하는 one-shot 어댑터다.

Principle 02

딱 두 시점에만 동작

실행 전 성공 기준(Spec) 감사, 실행 후 답(Answer) 채점. 그 사이 에이전트 실행에는 관여하지 않는다.

Principle 03

판정과 점수의 분리

LLM은 원자 단위 사실 판정만 반환한다. task_success는 사람이 짠 결정론적 policy.py가 계산한다 — 프롬프트를 바꿔도 점수 의미가 몰래 바뀌지 못한다.

Principle 04

기계 판정 ≠ 사람 검수

LLM 판정은 항상 machine_adjudicated로 표기하며 human review로 위장하지 않는다. 근거 부재는 부재의 증명이 아니다.

04

데이터 계약 — 주고받는 데이터의 정해진 형식

쉽게

"계약(contract)"은 부품끼리 주고받는 데이터의 정해진 서식이에요. 예를 들어 택배 송장에 반드시 "보내는 사람 / 받는 사람 / 무게" 칸이 있어야 하듯, 채점관이 반환하는 데이터도 칸이 미리 정해져 있어요. 여기서 핵심은 — 그 서식에 "최종 점수" 칸을 일부러 안 만들었다는 점이에요.

모든 판정은 형식이 고정된 데이터 객체로 오간다. 채점관 LLM이 답을 채점하면 TaskJudgment라는 서식으로 반환하는데, 이 서식에는 "합격/불합격" 같은 종합 결론 칸이 없다. 오직 잘게 쪼갠 개별 판정만 담긴다 — 종합은 뒤이어 정책 코드가 맡기 때문이다(7번 참고).

사후 채점 서식 — 채점관이 채우는 칸들

# 채점관 LLM이 반환하는 "답안 채점표". 종합 합격 여부 칸은 일부러 없음.
TaskJudgment = {
  fact_judgments   : [ 필요한 사실마다 → 답에 담겼나? (담김 / 부분 / 안 담김) ],
  claim_judgments  : [ 답 속 주장마다 → 근거가 뒷받침하나? (지지 / 반박 / 불명) ],
  behavior         : 올바르게 행동했나? (답할 상황에 답했나 등),
  answer_relevance : 질문에 맞는 답인가? (맞음 / 부분 / 엉뚱),
  indeterminate_reason : 판단이 불가능했다면 그 이유
}

즉 채점관은 "이 사실은 담겼고, 저 주장은 근거가 없고…" 같은 작은 사실 판단만 칸칸이 채운다. 이 조각들을 모아 점수를 내는 일은 채점관의 몫이 아니다.

사전 판정 서식 — 다섯 개의 합격 체크

시험 전 기준 검사(5번 Phase 1)에서 채점관이 채우는 서식에는 합격 조건 다섯 개가 예/아니오로 들어간다. 그리고 다섯 개가 전부 "예"일 때만 최종 판정을 accept로 적을 수 있다 — 하나라도 "아니오"인데 accept로 적으면 서식 자체가 거부된다(코드가 강제).

합격 체크쉽게 말하면
problem_spec_aligned이 성공 기준이 사용자가 진짜 원한 것을 대표하나?
required_facts_supported성공에 필요한 사실마다 뒷받침 근거가 최소 1개씩 있나?
answerability_consistent"답할 수 있는 문제"라는 표시가 실제 근거와 맞나?
behavior_consistent기대하는 행동(답하기/되묻기)이 문제 성격과 맞나?
tool_independent특정 검색 방식(BM25·Dense 등)에 의존하지 않는 기준인가?
05

Phase 1 · 스펙 판정 (시험 전)

쉽게

학생을 채점하기 전에, 시험 문제와 정답 기준이 제대로 됐는지 먼저 감수하는 단계예요. 기준이 틀리면 이후 채점이 다 헛수고니까요. 믿음을 위해 똑같은 검사를 두 번 따로 돌려서, 둘 다 통과할 때만 그 문제를 시험에 씁니다.

여기서 "스펙(Spec)"은 한 문제의 성공 기준을 뜻한다. 에이전트를 돌리기 전에 이 성공 기준 자체를 감사한다. 같은 스펙을 독립적으로 두 번 판정하고, 두 번 다 accept이며 다섯 체크의 결과(예/아니오 조합)까지 완전히 같을 때만 승격한다.

검사를 시작하기도 전에 거르는 조건

다음 중 하나라도 걸리면 아예 채점관을 부르지 않고 즉시 반려한다.

  • 문제-기준 짝 불일치 — 문제와 성공 기준의 id가 다르면 잘못 묶인 것이므로 거부.
  • "답할 수 있는 문제"만 허용 — "모른다고 답해야 하는 문제"는 이 단계에서 다루지 않는다. 근거가 비어 있다는 사실만으로는 "근거가 없다"를 증명할 수 없기 때문이다. (이런 문제는 별도의 전수 조사 절차가 필요하다.)
  • 근거 최소 1개 필요 — 답할 수 있는 문제인데 뒷받침 근거가 하나도 없으면 거부.
  • 엉뚱한 사실 지목 차단 — 채점관이 문제에 없는 사실 항목을 지목하면(환각) 거부.
왜 두 번

한 번의 판정은 우연히 통과할 수 있다. 두 번의 독립 검사가 모두 accept하고, 다섯 체크의 예/아니오 조합까지 완전히 같을 때만 승격한다 → 신뢰도 확보. 실제 결과: 통과 111 · 탈락 10 · 엇갈림 0건.

06

Phase 2 · 답 채점 (시험 후)

쉽게

에이전트가 답을 낸 뒤에, 그 답을 채점하는 단계예요. 단 학생이 실제로 찾아온 자료만 가지고 채점하고, 정답지는 채점관에게 안 줘요(베끼기 방지). 그리고 채점관은 사실 판단까지만 하고 — 점수는 안 매기고 멈춰요.

에이전트가 답을 낸 뒤, 그 답을 실제로 가져온 근거에 대해서만 채점한다. 채점관은 앞서 본 TaskJudgment 서식(사실·주장·행동·관련성)만 채우고 그 지점에서 멈춘다. 이후 검증과 점수 계산은 코드가 이어받는다.

채점 결과를 받아들이기 전 코드가 확인하는 것

  • 사실 항목 빠짐없이 — 채점관이 채운 사실 항목이 성공 기준의 필요한 사실과 정확히 일치해야 한다. 누락·초과는 거부.
  • 없는 근거 인용 차단 — 채점관이 인용한 근거가 학생이 실제로 가져온 자료 안에 없으면 거부. 채점관이 근거를 지어낼 수 없다.
  • 버전 일치 — 채점에 쓴 모델·프롬프트·서식 버전이 기록과 다르면 채점 거부.
  • 학생이 지어낸 근거는 실패가 아님 — 학생(에이전트)이 없는 자료를 지어냈다면, 그건 채점관의 오류가 아니라 진단 신호로 따로 표시된다.
07

결정론적 정책 — 점수의 진짜 정의

쉽게

"결정론적"은 같은 입력이면 언제나 똑같은 결과가 나온다는 뜻이에요 — 그날그날 기분이나 해석에 따라 안 바뀌죠. 최종 합격/불합격은 채점관 AI가 아니라, 사람이 미리 짜둔 계산 규칙이 정합니다. 그래서 채점관의 말투를 바꿔도 점수 기준은 절대 안 흔들려요.

이것이 설계의 핵심축이다. LLM이 아니라 정책 코드가 최종 task_success를 계산한다. 규칙이 코드로 고정돼 있으므로, 프롬프트를 어떻게 바꿔도 점수의 의미가 몰래 달라지지 않는다.

"답할 수 있는 문제"의 합격 조건 — 아래를 전부 만족해야 성공
행동이 올바름그리고 답할 상황에 제대로 답했다
필요한 사실 100% 전달그리고 부분 전달은 0.5점, 하나라도 빠지면 탈락
질문 관련성 ≥ 0.5그리고 엉뚱한 답이 아니다
근거 뒷받침 ≥ 90%그리고 지어낸 말(환각)이 거의 없다
판단 불능이 아님 채점관이 "모르겠다"로 멈추지 않았다

각 지표를 계산하는 방식:

  • 사실 전달률(coverage) — 필요한 사실마다 담김 1점 · 부분 0.5점 · 안 담김/반박 0점을 매긴 평균.
  • 근거 뒷받침률(groundedness) — 답 속 주장 중 근거로 지지된 비율. 주장이 하나도 없으면 계산 안 함(빈 값).
  • "모른다고 답해야 하는 문제"는 규칙이 다르다 — 이 경우엔 지어낸 주장이 하나라도 있으면 실패다. 즉 사실을 만들어내지 않고 솔직히 모른다고 하는 것이 성공이다.

덤으로 나오는 검색 품질 진단

정책은 합격 여부와 별개로, 학생이 검색을 얼마나 잘했는지 진단도 낸다: 필요한 근거를 얼마나 찾았나(recall), 가져온 것 중 쓸모 있는 비율(precision), 순위 품질(nDCG) 등. 이건 성공 점수가 아니라 왜 성공/실패했는지 원인을 설명하는 참고 자료다.

08

격리 불변식 — 오염을 막는 벽

쉽게

"불변식"은 어떤 상황에서도 항상 지켜지도록 코드가 강제하는 규칙이에요. 사람이 "그러지 말자"고 약속하는 게 아니라, 어기면 프로그램이 아예 거부하게 막아둔 거죠. 규칙 하나하나가 커닝·조작 경로 하나씩을 봉쇄해요.

이 시스템의 신뢰성은 아래 규칙들이 사람의 선의가 아니라 코드 수준에서 강제된다는 데서 나온다. 왼쪽이 규칙, 가운데가 그 규칙이 막는 부정 경로다.

강제되는 규칙막는 부정행위위치
채점관 설정은 학생 설정을 물려받지 않음채점관이 학생과 같은 조건에 물들기config.py
학생에겐 발화·맥락만 전달정답·기준 누출 (커닝)controlled_runner
정답지를 채점관에게 안 줌정답 베끼기 채점task_grader.py
채점관은 최종 점수를 못 냄프롬프트로 점수 조작contracts / policy
인용은 학생이 가져온 자료로 제한없는 근거 날조task_grader.py
근거 자료는 지문(해시)으로 검증변조된 자료로 채점world_evidence.py
서버 오류는 채점 실패로만 표시인프라 오류를 학생 실패로 오계산gemini_client.py
AI 판정은 "기계 판정"으로 표기기계 판정을 사람 검수로 위장materialize.py
09

불변성 · 체크포인트 · 재현성

쉽게

원본 데이터는 절대 덮어쓰지 않고 항상 새 사본을 만들어요. 그리고 각 데이터에 지문(fingerprint)을 남겨서 나중에 "이게 진짜 그 데이터가 맞는지" 확인할 수 있게 하죠. 작업이 중간에 끊겨도 이어서 할 수 있고요.

  • 원본 불변 — 판정 결과를 만들 때 원본을 절대 고치지 않고 새 스냅샷을 생성한다. 출력 폴더가 이미 있으면 거부한다(실수로 덮어쓰기 방지).
  • 전부 쓰고 나서 확정 — 임시 폴더에 전체를 다 쓴 뒤에야 정식 이름으로 바꾼다. 중간에 실패하면 .failed- 표시로 남겨 흔적을 보존한다.
  • 체크포인트로 이어하기 — 항목마다 진행 상황을 기록한다. 각 기록에 원본의 지문을 새겨서, 다른 원본의 체크포인트를 잘못 재사용하려 하면 거부한다.
  • 지문(해시) 추적 — 기준·응답·결과 데이터 모두 SHA-256 지문을 남긴다. 같은 지문 = 같은 데이터임이 수학적으로 보장된다.
  • 사본도 아직 "정식 아님" — 기계 합의는 사람 검수도, 출시 승인도 아니므로 이 사본은 출시용이 아니라 채점기 개발용이다.
10

운영과 실행

쉽게

실제로 돌릴 땐 먼저 연결 테스트(preflight) 한 번, 그다음 본 판정(adjudicate) 순서예요. 돈이 드는 실제 호출이라, 실수로 못 돌리게 확인 스위치를 반드시 켜야 실행돼요.

채점관 설정은 EVAL_JUDGE_* 환경변수로만 조정되고 에이전트 설정과 분리된다. 모델은 gemini-3.7-flash로 고정, 실행에는 Google Cloud 프로젝트와 인증(ADC)이 필요하다.

# 1) 연결 확인 — 채점관에게 딱 1번 물어보기
python -m launchpilot.evaluation.judging.cli preflight

# 2) 본 판정 — 실제 비용 발생, 확인 스위치 필수
python -m launchpilot.evaluation.judging.cli adjudicate \
  --dataset-root evals/datasets/marketing-ops-task-v1 \
  --output-root  evals/datasets/marketing-ops-task-2026-08-judge-ready \
  --rubric       evals/rubrics/spec-adjudication-v1.yaml \
  --checkpoint   evals/runs/spec-adjudication-2026-08.checkpoint.jsonl \
  --confirm-live-calls   # ← 이 스위치가 없으면 실행 거부
  • 비용 안전장치 — --confirm-live-calls 없이는 실행을 거부한다(예상 호출 수 = 검사할 문제 × 2회).
  • 이어하기 — 중간에 멈춰도 체크포인트부터 이어서 판정한다.
  • 재시도 — 일시적 오류(408·429)와 서버·형식 오류만 잠깐 기다렸다 다시 시도한다(기본 2회). 그 외 오류는 즉시 실패 처리.
  • 비용 분리 기록 — 채점관이 쓴 시간·토큰·비용은 학생 시스템의 것과 별도 칸에 기록된다.
11

현재 지위와 다음 게이트

쉽게

지금은 "시스템이 잘 돌아가는지 골격을 확인한" 단계이지, 정식 성적표를 낼 완성 단계가 아니에요. 실제 고객 사례가 아직 없고, 문제들도 전부 "검토 필요" 상태라서요.

현재의 판정 사본은 합성 데이터로 연결·정합성만 검증한 결과다. 사람 선호도 보정(calibration)이 아니므로 출시 벤치마크가 아니다.

다음에 할 일 (순서대로)

  • 탈락 10건 다시 쓰기 — 필요한 사실과 양쪽 근거를 보강한다.
  • 근거 부족 29건 검증 — 전수 조사 절차로 "정말 근거가 없는지" 확인한다.
  • 실제 사례 모으기 — 비식별 처리한 실제 고객 사례를 수집해 분포를 본다.
  • 누출 방지 분리 — 학생이 미리 못 보게 별도의 "봉인된 시험지(Holdout)"를 만든다.
  • 채점관 자체 검증 — 사람 검수가 어려우므로, 일관성 테스트로 채점관이 믿을 만한지 따로 검증한다.
